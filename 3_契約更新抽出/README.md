# 有期契約職員 契約更新対象者抽出デモ（3ヶ月契約の抽出漏れ対策）

> **社内デモ用です。データはすべて架空（`DEMO-xxxx` / 「架空」付き氏名・AM名）で、実在の人物・組織とは関係ありません。メール送信・外部連携は一切行いません。**

想定案件：CrowdWorks「雇用契約の更新対象者抽出・確認・進捗管理の自動化」（月平均約243名・AM約35名）。
本デモは第一段階のうち **「対象者抽出 → AM別一覧・確認依頼文の作成」** までを、ローカルの Python で再現したものです。

## 構成

```
crowdworks-demo3-keiyaku/
├── generate_staff.py      # 架空の職員CSVを生成（エッジケース・データ不備を意図的に混入）
├── renewal.py             # 日付計算・抽出・旧方式（比較用）のコアロジック
├── extract_renewals.py    # CLI：抽出 → xlsx / csv / AM別確認依頼文
├── tests/test_renewal.py  # pytest（境界値・閏年・性質テスト）
├── data/staff.csv         # 生成済みサンプル（250名、seed=20261011、基準日 2026-10-11）
└── output/
    ├── 更新対象者_2026-11.xlsx / .csv          # 2026年11月満了分
    ├── messages_2026-11/確認依頼_*.txt         # AM別 確認依頼文（13件・未送信）
    └── 更新対象者_2026-11_+1.xlsx / .csv ほか  # 翌月末（12月）までの先読み版
```

## 使い方

```bash
pip install -r requirements.txt
python generate_staff.py                                   # data/staff.csv を再生成
python extract_renewals.py --month 2026-11                 # 11月満了分
python extract_renewals.py --month 2026-11 --lookahead 1   # 翌月末（12月末）まで
python extract_renewals.py --month 2026-11 --convention minus1 --deadline 2026-10-20
python -m pytest -q tests
```

| オプション | 意味 |
|---|---|
| `--month YYYY-MM` | 対象月（この月に契約期間が満了する人を抽出） |
| `--lookahead N` | N ヶ月先の月末まで含める（1 = 「翌月末まで」）。1人1行・最も早い満了日で表示し、複数回満了する1ヶ月契約者にはフラグ |
| `--convention` | 終了日の規約（下記）。既定 `civil` |
| `--deadline` | AM への回答期限。既定は対象月の前月20日 |

## 入力CSVの列

`職員ID, 氏名, エリア, エリアマネージャー, 契約開始日, 契約期間(月), 契約終了日, 更新回数(反映済), 在籍状態, 備考`

- **契約開始日** = 当初（初回）契約の開始日。以後は同じ期間で自動更新される前提。
- **契約終了日** = 給与ファイル上の値を模したもの。空欄・現行期・**1期前（前回更新が未反映）** が混在。本ツールは**この列を判定に使わず**、整合チェックにのみ使います。
- **在籍状態** = 在籍 / 休職中（対象・フラグ付き）/ 退職予定（除外シートへ）/ 退職済（無視）。

## 終了日の計算ルール

第 k 期（k=1 が当初契約）の終了日を、**当初開始日（起算日）から直接** `起算日 + k×N ヶ月` を求めて決めます（`dateutil.relativedelta`）。
前期の終了日から連鎖的に計算すると、月末の切り詰めが累積して（1/31→2/28→3/28…）日付がずれていくためです。

| 規約 | ルール | 11/30開始・3ヶ月 | 1/31開始・1ヶ月 | 4/1開始・3ヶ月 |
|---|---|---|---|---|
| `civil`（既定） | 民法143条型：応当日の前日に満了。応当日がない月はその月の末日 | 2/28（閏年 2/29） | 2/28 | 6/30 |
| `minus1` | 開始日 + Nヶ月 − 1日（存在しない日は月末に切り詰めてから −1日） | 2/27（閏年 2/28） | 2/27 | 6/30 |
| `calendar` | 月末締め：開始月を1ヶ月目とし N×k ヶ月目の末日 | 1/31 | 1/31 | 6/30 |

- 1日開始は、どの規約でも「前月末日」満了（4/1開始3ヶ月 → 6/30）。
- 期間は必ず隙間なく連続し（第k期終了日の翌日 = 第k+1期開始日）、各期の満了は必ず別々の月に1回だけ来ます（テストで検証）。
- 実際の就業規則・契約書の書き方に合わせて規約を選んでください（**要確認事項**）。
- 生成データの「契約終了日」列は `civil` で作っているため、`--convention minus1` で実行すると周期不一致の警告が増えます。これは「規約の取り違え」を検知できる例でもあります。

## 抽出ルール

1. 対象月（〜先読み月末）に満了する期があれば対象。
2. `退職予定` は対象から外し「除外(退職予定)」シートに一覧（念のため確認用）。
3. データ不備は「データ要確認」シートへ：
   - **エラー（判定不能）**：開始日空欄・存在しない日付（2025-02-30 等）・想定外の契約期間・ID重複
   - **警告（対象には含める）**：AM空欄（「AM未設定・要確認」シートへ振分け）、契約終了日列が周期と不一致（期間変更・規約違いの可能性）
4. 各対象者に参考情報を付与：
   - **雇止め予告期限(30日前)**：更新3回以上 または 通算1年超 の人（厚労省告示の目安）
   - **無期転換見込**：次期で通算5年を超える人（クーリング期間等は未考慮）
   - **終了日列が未反映**：給与ファイルの終了日が前期以前のまま

## なぜ旧来の方法で3ヶ月契約者が漏れるのか

案件説明にある「**前回の更新内容が職員給与ファイルへ反映される前に次回の抽出時期を迎える**」がポイントです。
3ヶ月契約は「更新 → 給与ファイル反映」のサイクルが短く、反映待ちの間に次の抽出月が来ます。代表的な失敗パターンを3つ実装し、正しい抽出と比較しました（`renewal.py` の `naive_*`）。

| 旧方式 | 内容 | 何が起きるか |
|---|---|---|
| A: 終了日列をそのまま参照 | 「契約終了日」列が対象月の人を抽出 | 列が**前期のまま（未反映）**や**空欄**の人が漏れる。3ヶ月契約で特に多い |
| B: 四半期末一斉と仮定 | 3ヶ月契約は 3/6/9/12 月に満了と決め打ち | 開始月が四半期とずれた人（2/5/8/11月開始など）は**対象月に一切出てこない**／逆に該当しない月に誤抽出 |
| C: 開始「月」だけで周期判定 | (対象月 − 開始月) が N の倍数なら対象 | 日を無視するため、**1日開始（前月末満了）**の人が1ヶ月ずれる（漏れ＋誤抽出） |

### 2026年11月の比較結果（サンプルデータ、3ヶ月契約者のみ）

| 方式 | 抽出数 | 正しい対象 | 漏れ | 誤抽出 |
|---|---|---|---|---|
| 本ツール（起算日から周期計算） | 37 | 37 | 0 | 0 |
| 旧方式A：終了日列参照 | 18 | 37 | **19**（未反映15・空欄4） | 0 |
| 旧方式B：四半期末前提 | 0 | 37 | **37** | 0 |
| 旧方式C：開始月のみ | 36 | 37 | **12** | 11 |

同じ表は xlsx の「サマリー」シート下部にも出力されます。

## 出力

- **xlsx**
  - `サマリー`：AM別（契約期間別内訳・フラグ件数）、エリア別、契約期間別、旧方式比較
  - `AM名`シート（AMごと）：対象者一覧（満了日順）。3ヶ月契約を緑、フラグを黄色で強調。「更新可否」欄はプルダウン（更新／終了／要相談）、黄色セルがAM記入欄。横向き・幅1ページ印刷設定
  - `（AM未設定・要確認）`、`除外(退職予定)`、`データ要確認`
- **csv**：対象者一覧（UTF-8 BOM、Excelでそのまま開ける）
- **確認依頼文**（`messages_*/確認依頼_<AM名>.txt`）：AM名・人数・3ヶ月契約人数・満了日範囲・回答期限・対象者リストを差し込み済み。回答期限より前に雇止め予告期限が来る人は★で明示。担当者名などは `{担当者名}` のまま残しています。**送信機能はありません。**

## テスト

`python -m pytest -q tests` → **62件すべて成功**。主な内容：

- 3ヶ月の境界：11/30・8/31開始（2/28・2/29満了）、1日開始（前月末）、四半期非整合（8/12開始→11/11）
- 月末：31日・30日開始の1ヶ月連鎖（1/31→2/28→3/30→4/30）、ドリフトしないこと
- 閏年：2027-11-30開始→2028-02-29、2028-02-29開始12ヶ月→2029-02-28、4年後は 2032-02-28
- 1/6/12ヶ月の代表ケース、3規約の差異
- 性質テスト：約400の開始日×4期間×3規約で期間の連続性、24ヶ月間で**各人がNヶ月おきにちょうど1回・抜けなし**、3ヶ月契約は24ヶ月で必ず8回
- 抽出：退職予定除外・退職済無視・不正日付・想定外期間・ID重複・AM空欄・周期不一致・未反映の終了日列でも漏れないこと
- 生成データ全体：2026年の24ヶ月で各人が1ヶ月に1回以下・周期どおりに出現

## 制約・今後の拡張

- **終了日規約**は実際の契約書・就業規則を確認して選ぶ必要があります（初日算入の扱い、月末締めの有無など）。
- **期間途中の変更**（3ヶ月→6ヶ月への変更、期間短縮、再雇用、異動によるAM変更）は「当初開始日＋一定周期」の前提を崩します。本番では**契約更新履歴テーブル**（期ごとの開始日・終了日・期間）を正とし、最新の期から先を計算する方式にすべきです。本デモでは周期不一致の警告で検知するのみです。
- **AMの特定**は CSV の列をそのまま使っています。本番では所属事業所×異動履歴×AMマスタの最新照合が必要です。
- **雇止め予告（30日前）**：サンプルでは11月満了の対象者のうち、予告対象と思われる21名の予告期限が既定の回答期限（10/20）以前、うち9名は作成日（10/11）時点で既に経過しています。実運用では**2ヶ月先までの先読み抽出**（`--lookahead 1` 以上）と回答期限の前倒しを推奨します。休日を考慮した期限調整は未実装です。
- **無期転換（通算5年）**は単純計算の目安のみ。クーリング期間・空白期間・契約通算の詳細判定は未実装です。
- 実データの形式（列名、日付形式、和暦、Excelシリアル値、文字コード）は不明のため、取込部分は要調整です。
- 回答の回収・未回答リマインド・職員情報更新用データ作成（案件のステップ④〜⑥）、権限管理・操作ログは対象外です。
